Implement a new profile format end-to-end.

# Format

$ARGUMENTS

# Principles

- Trust real profiler output over the spec. Real files may violate it. Consider
  parsing correct only after a generated real input validates it, not just
  hand-written tests

- Verify against ground truth you compute independently. Before trusting the
  Markdown output for a real input, write a throwaway script that tallies
  checkable invariants straight from the input bytes (e.g. summed self costs
  must equal the file's `summary:`; per-function totals from an independent
  parse) and compare against the formatted tables

- Follow the @../../dimensions.md principles for every behavior an input shows

# Workflow

## Research

1. Read the format's official spec online

2. Read one or two reference implementations (e.g. the canonical viewer's
   parser, speedscope's importer). Note where they deviate from or extend the
   spec

3. Enumerate the tools and runtimes that emit the format (the canonical tool,
   other profilers that export it, tools we already support). A tool emits the
   format when it writes the format itself, so leave out the tools that convert
   another profiler's output into it. Then decide the origin question:
   - Note which existing origins need their `formats` expanded
   - Register each emitting tool or runtime we don't have yet as its own origin,
     even when its inputs carry no detectable markers (a markerless spec,
     `isMarkerEntry: () => false`); sharing another origin's spec would make a
     later behavioral split a breaking change
   - Decide the format's `fallbackOrigin`: the format's canonical origin, the
     tool or runtime whose definition of the format the other emitters write to
     match (e.g. `valgrind` for callgrind, `chrome` for the V8 formats). A
     format with several emitters still has a canonical origin. The canonical
     emitter may have its own markers. Use `unknown` when the format is defined
     by something that profiles nothing itself (e.g. the speedscope viewer,
     FlameGraph's stack-collapsing scripts, the pprof project). Record the
     reasoning in a comment above the field

4. For a format the call stack profile modality captures, determine what one
   unit of each profile's per-sample count measures, from the emitters' source
   or spec rather than the field names. One unit is a periodic sample of the
   call stack, an occurrence of something the profiler records (an entry, an
   allocation, an object, a contention), or a quantity that counts nothing, as
   when eflambe writes one collapsed count per microsecond. Note whether the
   emitters agree, since a format whose emitters disagree requires the answer
   per origin. See the counting principles in `CLAUDE.md`

5. For a format the call stack profile modality captures, determine whether each
   position the format records for a frame is where the function is defined or
   where the frame was when recorded, from the emitters' source or spec rather
   than the field names. Note whether the emitters agree. See the normalizing
   principles in `CLAUDE.md`

6. Enumerate what the format records about the machine or the session rather
   than the program (environment, process list, host and addresses, cookies,
   command line, user paths), and how the profiler suppresses each. Committed
   inputs are public, and `pnpm check-input-privacy` rejects the classes it
   recognizes, but a format can record something it does not

7. Confirm every modality the format captures is supported. If any is
   unsupported, STOP: explain the new modality and how it differs from the
   supported ones, and ask whether to implement it first by loading
   `/new-modality` and following its workflow

## Generate inputs first

8. Load `/new-input` and follow its workflow through generation and inspection
   for every emitting language; return here at its converter checkpoint, since
   the converter doesn't exist yet

9. Reconcile the generated bytes with the research: the parser plan must account
   for every construct in the real file without overfitting to it

## Implement

10. Create `src/formats/<name>/` with `parse.ts`, `matches.ts`, `index.ts` (the
    `<name>Converter`), and `index.test.ts`:
    - In `parse.ts`, rename a runtime activity the format spells its own way to
      the label the shared categorization already has (see
      `VM_STATE_FRAME_NAMES` in `src/formats/v8/heap-profile/parse.ts`) rather
      than widening `FunctionCategory`. Omit a field the format fills with a
      placeholder for missing information (a name, path, or line standing for
      "not known"). A placeholder a single profiler substitutes is omitted by
      its origin's `normalizeStackFrame`
    - For a call stack profile, take metrics from the constants in
      `src/modalities/metrics.ts`, adding one when the format measures something
      new, and call `parseMetric` only where the input names its own unit. For a
      lone count metric, populate `Observation.count` with no metrics. Set
      `countMetric` from step 4
    - Keep `matches` cheap and strict enough not to claim other text or JSON
    - Test `matches`, `parse` rejections, end-to-end conversion with the helpers
      in `src/formats/testing.ts` and the modality's `testing.ts`, and the
      tricky behaviors the real inputs exposed

11. Implement the origin decision from step 3: for each new emitting tool or
    runtime, load `/new-origin` and follow its workflow.

Then set up the format's origin detection:

- List the format in the `formats` of every origin that emits it
- A missing per-origin `formats` entry fails silently (detection falls back).
  The detected-input-origins test in `src/origins/index.test.ts` requires every
  committed input to resolve to the origin in its filename. NEVER commit an
  input that resolves elsewhere: give the origin a marker or a parser origin
  hint, or make the workload realistic enough to carry the origin's evidence

## Register

12. Add the converter to `formatConverters` in `src/formats/registry.ts`

13. `src/cli/languages.ts`: add a `languageMetas` entry (name, aliases,
    extensions) for any emitting language we don't list yet. An origin's display
    name comes from its `OriginSpec.title`; if a new config token needs a
    display label beyond title-casing, add it to `configNames` in
    `src/cli/examples.ts`

## Validate against real inputs

14. Convert each generated input with `node src/cli/index.ts <input>` and verify
    against independently computed ground truth. Also convert each base/current
    pair as a diff. Expect this step to send you back to step 10; that's the
    point

15. `pnpm bench <input>` to confirm conversion time is comparable to existing
    formats on similar-size inputs

## Document and finish

16. `docs/formats/<name>.md` for `--help <format>`; generation instructions in
    each emitting language's `docs/languages/<language>.md` (a new file for a
    new language). Verify the content renders with
    `node src/cli/index.ts --help <name>` for the format and each language

17. `pnpm update-examples` (re-run after ANY later converter change), then
    `pnpm update-readme`

18. `pnpm format`, `pnpm lint`, `pnpm typecheck`, `pnpm knip`, `pnpm test`
